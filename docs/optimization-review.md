## 0. 先看懂这条流水线（每次优化打在哪个环节）

```
视频 / 摄像头
   │
   ├─① YOLO26n-Pose   每帧输出若干"人"候选
   │                  每个候选 = bbox + bbox score + 17 个关键点(坐标 + 各自的置信度)
   │
   ├─② 质量门 PoseExtractor._is_valid_person   决定哪些候选"像是人"，喂给下游
   │
   ├─③ PersonTracker   给目标分配稳定 ID 并跨帧维持（质心匹配 + IoU 兜底 + 轨道确认）
   │
   ├─④ 每人 30 帧缓冲 SequenceBufferV3         按 track id 隔离
   │
   ├─⑤ 192 维特征 FeatureBuilderV2
   │                  每帧 64 维 = 17×(x,y,conf)=51 + 原始几何 6 + 增强几何 7
   │                  再拼 pos(64) + vel(64) + acc(64)
   │
   ├─⑥ LSTM 分类头 RiskClassifierV2
   │                  4 类(SAFE/FALLEN/SITTING/NON_PERSON) + 风险回归 + 跌倒时间回归
   │
   ├─⑦ RiskEngineV2 状态机   SAFE / WARNING / DANGER
   │                  （EMA 平滑 + 连续计数 + 锁定保护）
   │
   └─⑧ 画面显示 draw_result / draw_lost_result
```

| 优化 | 打在哪一环 |
|---|---|
| 1 · 多人混写缓冲区 | ③④⑤ |

| 3 · 动作幅度大就丢对象 | ③ |
| 4 · 建难例集与评估工具 | 全部（基础设施） |
| 5 · 质量门两段式 | ② |
| 6 · NON_PERSON 样本为 0 | ⑥（诊断） |
| 7 · 降 conf + 抬 WARNING 阈值 | ②⑦ |
| 8 · 车类交叉验证（失败） | ② |

## 2. 逐条详解

### 优化 1 · 画面有第二个人时，正常行走被误报 FALLEN

**① 发现什么问题**

用户反馈"人稍微动动很多时候也会报 falldown"。在 `person_falldown-1.mp4` 上复现：
老人**第 118–125 帧**才真的跌倒，但**第 90 帧（人还在走路）**界面就已经报 `FALL`。

**② 解决思路**

先分清是"模型的问题"还是"喂给模型的输入有问题"。做法是拿**训练侧**和**推理侧**的预处理逐行对照：

- 训练侧 `extract_keypoints.select_person()`：每帧**只取一个人**（`kpts_conf.sum()` 最大者）
- 推理侧 `realtime_detect.py`：`person_id = 0` **硬编码**，却 `for person in persons` 把画面里
  N 个人全部写进**同一个** 30 帧缓冲区

→ 找到不一致。但"找到不一致"还不算修，先量化它的影响：测缓冲区相邻两项的特征差。

> **考虑过但放弃的方向**：换模型、加训练数据。如果是预处理错，加数据救不了 —— 先定位再决定。

**③ 执行步骤 / 改了什么**

| 文件 | 改动 |
|---|---|
| `realtime_detect.py` | 接入 `PersonTracker`，主循环改为遍历 `tracks`，用 `track["id"]` 索引缓冲区与风险引擎；`removed_ids` 到达时清理状态 |
| `tracker/track.py` | 新增并全程透传 `kpts_conf` / `score` |
| `pipeline/risk_engine_v2.py` | 新增 `remove(person_id)`，避免 ID 累积 |

> 透传 `kpts_conf` 是必须的：`Track` 原先不带它，直接用会让 `FeatureBuilderV2.build()`
> 以 `np.ones(17)` 兜底 —— **17 个 conf 维静默退化成常量 1.0**，不报任何错。

**④ 最终结果**

| `person_falldown-1.mp4` | 改前 | 改后 |
|---|---|---|
| 缓冲区相邻条目特征平均差 | **10.12**（跨人交替） | **0.85**（同一人相邻帧） |
| 跌倒前（<118 帧）误报 DANGER | 20 次（首个第 108 帧） | **1 次**（第 117 帧 = 真实跌倒起始） |
| 跌倒前误判 FALLEN | 31 帧，首个第 90 帧 | **0** |
| 行走阶段 p_fall | 爬升到 0.761 | 全程 < 0.01 |

### 优化 2 · 目标丢失后残留历史框

**① 发现什么问题**

镜头切换后画面里已经没人了，但那个人的红色 `ID:1 FALL` 框还留在原位置；
而且画面右侧**还有另一位刚走出来的男子**却在报"跌倒"。

**② 解决思路**

先判断是"显示问题"还是"推理问题"（会不会是缓冲区里混进了旧数据）。读代码后确认是显示逻辑：

1. `PersonTracker(max_missing=60)` 会保留丢失目标 60 帧（本意是容忍遮挡）
2. 丢失期间 `track["bbox"]` 是最后一次匹配的框，**位置被冻住**
3. `display[track_id]` 缓存了最后一次推理的 `state="DANGER"`，`missing > 0` 时把它重画

其中一条**是自己接入跟踪器时引入的**：原代码把这段放在 `if len(persons) == 0:` 里
（只有画面里一个人都没检出时才画），改成按 track 判断后变成"只要某个 track 丢失就画"。

用户猜测是"复用上一帧特征填充缓冲区"造成的 → 设计 **A/B 实验**排除。

**③ 执行步骤 / 改了什么**

- 新增 `draw_lost_result()` / `_draw_dashed_rect()`：灰色**虚线**框 + `ID:N FALL (lost Nf)`
- 主循环按 `has_live_target = len(persons) > 0` 分流：

  | 画面里是否有活体目标 | 显示 |
  |---|---|
  | 有 | 只留顶部 `FALL SUSPECTED (target lost)`，**不画任何框** |
  | 无 | 顶部报警 + 灰色虚线历史框 |

- 状态栏改单一优先级（原先两处都画在 `(10,50)` 会叠字）

**④ 最终结果**

| `person_falldown-3.mp4`（990 帧） | 改前 | 改后 |
|---|---|---|
| 画历史框的帧 | 181 | 67 |
| 其中**画面里还有人被检出** | **114** | **0** |
| 连续绘制片段长度 | `[60, 60, 60]` | `[7, 1, 59]` |

实时路径完全未变（pd1 首个 DANGER 仍是第 117 帧 / risk 0.5726）。

> **A/B 结论**：把"复用上一帧特征"那一行整行删掉重跑，第 83 帧的历史框**一字不差** →
> 用户的猜测被排除。但这次 A/B 顺带发现该填充有**另一个**副作用：它对丢失中的 ID 也会
> append 冻结特征，使其缓冲区更早凑满 30 帧；而训练侧对漏检帧是"零填充 + 插值"，
> 两者**口径不一致** → 记入遗留。

### 优化 3 · 动作幅度大就丢对象

**① 发现什么问题**

`person_falldown-3.mp4` 后段"人动作幅度大了会丢对象"——框突然消失，或换成一个新 ID 重新出现。

**② 解决思路**

不猜，把全片 **33 次新建 ID 逐个归因**，得到三条独立机制：

| 机制 | 占比 | 证据 |
|---|---|---|
| ① YOLO 直接漏检 | 主因 | 全片 **222/990 帧（22.4%）零检出**；后段连续零检出最长 32 帧 |
| ② 框变形使质心跳过 100px 阈值 | 8/33 | 这 8 次新框与已丢失轨道 **IoU ≥ 0.3**，但中心距全部 >100px（最小只超 0.1px） |
| ③ 单帧垃圾框产生僵尸轨道 | 11/39 | 只被匹配 1 次却挂 61 帧；过期 bbox 留在匹配池里抢占后续检测 |

> **顺带纠正一个直觉**：同一轨道自身的帧间中心位移**中位数仅 9.1px、最大 94.6px**，
> **从未越过 100px**。越阈值的是"框在变形"，不是"人跑得快"。

**考虑过但被数据否决的方向**：在质量门上加"bbox 合理性门"（框最小边、面积占比）。
实测真人与垃圾框严重重叠（f824 垃圾框占画面 22.0% / score 0.203，而 f245 **真人**框占 22.3% /
score 0.79），唯一干净的判据是检测置信度 —— 但那等于把 `conf` 抬回 0.3，与既有决策冲突。
**结论：空间阈值走不通 → 改用时间维度（轨道确认）。**

**③ 执行步骤 / 改了什么**

| 文件 | 改动 |
|---|---|
| `tracker/person_tracker.py` | 新增 `iou_threshold=0.3` **兜底匹配**：质心匹配失败后，若 IoU ≥ 0.3 仍判同一目标 |
| `tracker/person_tracker.py` | 新增 `min_hits=2` / `max_missing_unconfirmed=15` **轨道确认** |
| `tracker/person_tracker.py` | **两条路径都要改**（见下方踩坑） |
| `tracker/track.py` | 新增 `Track.is_lost()` 承载判定 |

`max_missing_unconfirmed=15` 取自实测：真人轨道"丢失后被找回"的间隔中位数 2、**p90 14**、最大 51。

**④ 最终结果**

| 指标 | 改前 | 改后 |
|---|---|---|
| 新建 ID 次数 | 39 | **31**（正好消掉那 8 次） |
| 单帧僵尸轨道寿命 | `[61]×11` | `[16]×10`（**−74%**） |
| Le2i 跌倒 5 段首 WARNING/DANGER | — | **逐帧一致**（能力未被削弱） |
| Le2i 正常 9 段 | 全 0% | 全 0% |

> **踩坑**：`PersonTracker.update()` 里"本帧无人"的**提前返回分支**独立维护了一份移除逻辑，
> 只改主循环不生效。由于该素材后段全是零检出帧，僵尸轨道照样活 61 帧。
> 用一个 **20 行最小复现**（喂 1 帧检测后连续喂空帧，打印 `removed`）才暴露出来。
> → **改动多处重复逻辑时，每条路径都要单独验证。**

### 优化 4 · 建立难例集与评估工具（基础设施）

**① 发现什么问题**

在 6 段真实素材上"感觉"夜间召回几乎为 0，但**没有可对比的数字**，任何改动都无法判断好坏。

**② 解决思路**

要一套"能重复跑、能量化、能横向比较"的评测，并解决一个关键盲点：
只知道"最终有没有框"无法区分**是模型没检出**还是**流水线把框滤掉了**。
所以评测同时报两个数字：**裸 YOLO** 与**完整 pipeline** —— 两者的差就是"流水线自己滤掉了多少"。

三步：导出候选帧 → 人工标注"帧里到底有没有人" → 评测。

**③ 执行步骤 / 改了什么**

| 文件 | 作用 |
|---|---|
| `scripts/build/export_hard_cases.py` | 导出候选帧（`hard` / `negatives` 双模式，重复运行保留人工标注） |
| `scripts/eval/eval_hard_cases.py` | 同时报裸 YOLO 与完整 pipeline 的召回/误报 |
| `scripts/eval/sweep_detection_gate.py` | 三种规则 × `conf` 档位的召回/误报对比 |
| `hard_cases/labels.csv` | 人工标注 **114 帧**（正 105 / 负 9） |

后来陆续补充：`scripts/eval/eval_pipeline_regress.py`（端到端回归）、
`scripts/eval/eval_nonperson_effect.py`（类别生效检查）。

**④ 最终结果**

第一次有了可信基线：

```
难例集: 已标注 114 帧（正 105 / 负 9）
  正样本召回    裸YOLO 104/105 (99.0%)    完整pipeline 52/105 (49.5%)
  负样本误报    裸YOLO 6/9 (66.7%)        完整pipeline 0/9 (0.0%)
```

**一半的正样本是被流水线自己滤掉的** —— 这个数字直接指向了优化 5。

### 优化 5 · 夜间/倒地场景漏检：质量门改为两段式判定

**① 发现什么问题**

难例集显示夜间场景召回极低：`person_falldown-3`（夜间雪地）**1/12 (8.3%)**、
`person_falldown-4`（夜间街道）**1/22 (4.5%)**、`fall_staircase-2`（夜间扶梯）3/13 (23.1%)。

**② 解决思路**

先找"框到底是被谁丢的"。结果很反直觉：

> 51 个"零检出"帧里，**47 帧裸 YOLO 其实给出了框**，是被 `PoseExtractor` 的质量门拒绝的。
> 而绝大多数只卡在**一条**：`平均关键点置信度 < 0.3`。

而这个 0.3 是在 **Le2i 白天室内**数据上标定的；夜间人物多为逆光/剪影或深色衣物，
**bbox 置信度正常但关键点置信度普遍偏低**（0.22–0.28）。

**关键设计（不是简单降阈值）**：把判据从"关键点低就拒"改成"**弱框 + 弱关键点**才拒"。
依据是同一帧内的对比：

| 目标 | bbox score | 关键点均值 | 该拒吗 |
|---|---|---|---|
| 夜间真人 pd3 f137 | **0.622** | 0.224 | 不该拒（框置信度高） |
| 夜间真人 pd3 f176 | **0.407** | 0.254 | 不该拒 |
| 室内沙发 | 0.07–0.26 | 0.21–0.26 | 该拒（两者都低） |

**③ 执行步骤 / 改了什么**

`pose/pose_extractor.py`：

```
mean_conf < 0.20                          -> 丢弃（硬下限）
mean_conf < 0.30 且 score < 0.30           -> 丢弃（弱框 + 弱关键点）
否则                                        -> 保留
```

同时**删掉 `extract()` 里那份硬编码 0.3 的重复过滤** —— 它与 `_is_valid_person` 是同一个条件的
两份实现，各改各的（本次正是靠删掉它才避免"只改一处"）。

**④ 最终结果**

| 指标 | 改前（单一 0.30） | 改后（复合门） |
|---|---|---|
| 难例集正样本召回 | 52/105 (49.5%) | **55/105 (52.4%)** |
| `fall_staircase-2`（夜间扶梯） | 3/13 (23.1%) | **8/13 (61.5%)** |
| Le2i 正常 7 段 | 全 0% WARNING/DANGER | 全 0% |
| Le2i 跌倒 5 段首次 WARNING/DANGER | — | **逐帧一致** |

> **踩坑（本项目最重要的一次）**：按难例集结论先把阈值直接降到 0.20，**难例集显示完全干净**
> （58.1% 召回、0/9 误报），但跑 Le2i 回归时 `Home_01 video(10)` 的**首次 DANGER 从第 112 帧
> 提前到第 50 帧** —— 而该视频标注的跌倒区间是 **135–150**，即第 50 帧的报警发生在**空镜头**里。
> 逐帧 A/B 定位到右下角一个**红色沙发**（关键点 0.21–0.26）通过了 0.20 → 家具特征喂给分类器 → DANGER。
>
> 这件事暴露了**难例集口径的盲区**：它只能表达"帧内是否有检出"，
> **无法表达"检出数多于实际人数"**。所以这类改动的守门测试必须是 **Le2i 端到端回归**。

### 优化 6 · 发现 `NON_PERSON` 类的训练样本是 0（纯诊断）

**① 发现什么问题**

### 优化 7 · 降低 `conf` 提召回，并抬高 WARNING 阈值

**① 发现什么问题**

`person_falldown-4.mp4` 里地上那位**跌倒老人只偶尔被框出来**（框闪烁）；

> **考虑过但放弃**：用"低分框要求更高关键点置信度"来打掉边缘黄框。
> 这**会直接误伤跌倒老人** —— 他正是 score 0.01–0.08 + 关键点 0.32–0.59 → 改用抬 WARNING 阈值。

**③ 执行步骤 / 改了什么**

| 文件 | 改动 |
|---|---|

| `pipeline/risk_engine_v2.py` | `warning_thres` **0.35 → 0.40** |

**④ 最终结果**

| 指标 | 改前 | 改后 |
|---|---|---|
| 难例集正样本召回 | 52/105 (49.5%) | **85/105 (81.0%)** |
| 难例集负样本误报 | 0/9 | 1/9 |
| Le2i 正常 7 段 | 全部 0% | **全部 0%** |
| Le2i 跌倒 5 段首次 DANGER | 298/147/197/140/112 | 299/147/197/142/116（延后 0–4 帧） |

分场景召回：`fall_staircase-1` 92.9%→100%、`fall_staircase-2` 23.1%→53.8%、
`person_falldown-2` 42.9%→85.7%、`person_falldown-4` **4.5%→77.3%**。

### 优化 11 · 时序编码器替换（LSTM → TCN）：受控消融，实测否定

**① 发现什么问题**

用户提出一个合理怀疑："摔倒是靠速度判断的，现在用 LSTM 做这件事，
是不是换成把 30 帧当矩阵喂的**视频模型**更好？"

先把事实摆清：**30 帧合成矩阵已经是现状**（输入就是 `(B, 30, 192)`），
LSTM 只是**作用在这个矩阵上的那个函数**。所以可验证的假设不是"换输入形态"，
而是"**换掉时序编码器**"。

顺带发现一处可疑设计：当前池化是

```python
pooled = 0.5 * out[:, -1, :] + 0.5 * out.mean(dim=1)
```

**末帧 + 均值各取一半** —— 均值会把"时序形状"（加速→减速的先后）压平，
末帧又丢掉过程，而"跌倒"恰恰是一个过程。

**② 解决思路**

做**单变量受控消融**：输入、数据、LOSO 折、超参、种子全部相同，**只换编码器**。
为了让比较的是"结构"而不是"容量"，把 TCN 的参数对齐到与 LSTM 同量级。
并且**每种编码器跑 2 个种子** —— 依据是优化 9 学到的教训：单种子对比里
基线自身跨度可达 12pp，会把噪声当结论。

**③ 执行步骤 / 改了什么**

| 文件 | 改动 |
|---|---|
| `classifier/risk_classifier_v2.py` | 新增 `TCNEncoder`（4 层膨胀 1/2/4/8 等长 Conv1d + GELU + LayerNorm + 残差，感受野 31 ≥ 窗口 30）；`RiskClassifierV2` 加 `encoder` 参数，**默认 `lstm` 保持原行为** |
| `classifier/lstm_classifier_v2.py` | 按 `state_dict` 键前缀自动识别编码器（老权重行为不变，权重自描述） |
| `scripts/train/train_v2.py` | 新增 `--encoder {lstm,tcn}`，默认 `lstm` |

容量对齐：LSTM 编码器 **296,960** 参数，TCN **222,848**（总参数 322,502 vs 248,390）。
两种编码器前向输出形状完全一致。

**④ 最终结果（否定）**

| 层面 | LSTM(2 seed) | TCN(2 seed) | 判定 |
|---|---|---|---|
| LOSO：SAFE / FALLEN / SITTING / acc | 95.45 / 82.59 / 78.85 / 92.58% | 95.00 / 83.30 / 80.88 / 92.45% | 全部落在**噪声带内**（SITTING +2.03pp 刚好压线） |
| 分类器层 NON_PERSON（held-out 1208 窗） | 66.4%（自身跨度 **12.2pp**） | 71.2%（跨度 3.3pp） | 差 4.8pp **小于**噪声带 → 无结论 |
| **端到端 · 真实 6 段 首DANGER** | **132.2 ± 9.8** | **196.9 ± 17.5** | **晚 64.7 帧**，两 seed **无重叠** ❌ |
| 端到端 · 跌倒 5 段 首DANGER | 180.3 ± 19.4 | 190.6 ± 2.8 | 晚 10.3 帧（噪声内） |
| 端到端 · 正常 7 段 | 两个 seed 全 0 ✅ | seed1 全 0；**seed2 的 `Office 19` 出现 19 帧 WARNING** ❌ | 违反硬门槛 |

**结论：架构不是瓶颈。** 换成 TCN 在离线指标上无差异、在端到端上更差 → **不采纳**。

**顺带拿到本项目第三次同类证据**：离线指标两者持平（TCN 的 SITTING 甚至略好），
但端到端明显更差 —— 又一次说明"**离线指标平/好 ≠ 端到端没问题**"。

> **踩坑**：等长 padding 写错（用了因果卷积的 `(k-1)*d` 却对称地加，
> 时间维 30 → 32，残差相加直接报错）；把 stdout 缓冲误判成"训练卡住"；
> 差点跑 `eval_hard_cases.py` 做回归——它**只走检测链、不经过分类器**，对本消融完全不敏感。

### 优化 12 · 时序池化替换（末帧 / 均值 / 最大 / 注意力）：受控消融，实测否定

**① 发现什么问题**

模型里有一处**手工设计**的池化：

```python
pooled = 0.5 * out[:, -1, :] + 0.5 * out.mean(dim=1)   # 末帧 + 均值各半
```

均值会把**时序形状**（加速→减速的先后顺序）压平，末帧又丢掉过程 ——
而"跌倒"恰恰是**一个过程**。上一轮换编码器是负结果，这次把范围收窄到**只动池化**。

**② 解决思路**

四种替代池化做单变量消融，其余全同（编码器仍为 LSTM）：
`last` / `mean` / `max` / `attn`（按时间步学习权重），控制组是现有 `lastmean`。

- **参数完全对齐**：四种变体都是 322,502 参数（`attn` 322,631，仅多 129），
  所以比较的是纯粹的**聚合方式**，没有容量混杂 —— 比上一轮 TCN 消融更干净。
- **每种池化 2 个种子**，判定仍以端到端为准（LOSO 只做筛选）。

**③ 执行步骤 / 改了什么**

| 文件 | 改动 |
|---|---|
| `classifier/risk_classifier_v2.py` | 新增 `pooling` 参数（默认 `lastmean`，既有行为不变）与 `AttentionPool` |
| `classifier/lstm_classifier_v2.py` | 优先读权重旁的 sidecar meta，缺失时按 `state_dict` 键推断 |
| `scripts/train/train_v2.py` | 新增 `--pooling`，保存权重时写 `models/*.meta.json` |

> **为什么必须写 meta**：除 `attn` 外，各池化变体的**权重键名完全相同** ——
> 只按键加载会**静默套用错误的池化**，结果全错却不报错。

**④ 最终结果（否定）**

| 池化 | 真实 6 段首DANGER（2 seed） | 与控制的差 | 正常 7 段 |
|---|---|---|---|
| `lastmean`（控制） | 127 / 137（均值 **132.2**） | — | ✅ / ✅ |
| `last` | 126 / 152（139.2） | +6.9 帧（噪声内） | ✅ / **❌ seed2 出现 WARNING** |
| `mean` | 146 / 159（**152.7**） | **+20.4 帧，超出噪声带** ❌ | ✅ / ✅ |
| `max` | 114 / 146（129.6） | −2.7 帧（噪声内） | ✅ / ✅ |
| `attn` | 139 / 166（152.8） | +20.5 帧（噪声内） | ✅ / **❌ seed2 出现 WARNING** |

**结论：没有任何替代池化优于现状。** 现任的"末帧 + 均值各半"反而是**稳健设计** ——
末帧经 LSTM 递归已编码全过程，均值对"末帧恰好被误检污染"有鲁棒性。这次实测给了它正面证据。

> **关键踩坑（差点又中招）**：`max` 在 seed 1 上曾显示真实组 **−13.8 帧**的"优势"，
> 补第二个种子后变成 **−2.7 帧、落回噪声内**。**只跑单种子就会得出"max 更好"的错误结论** ——
> 与优化 11 同一类型的坑，这次靠"两 seed + 预先定死判定规则"提前防住。

**结构性的第二块拼图**：连续两轮架构侧消融（编码器、池化）都是负结果，
共同支持"**瓶颈不在模型结构，而在输入信息与数据覆盖**"。

### 优化 13 · 把检测框 `score` 接进分类头：受控消融，实测否定

**① 发现什么问题**

优化 10 的诊断结论是"分类头的输入里没有判别信息，`score` 未入特征"，并把
"把 bbox score 放进分类头"列为下一步。本轮把它实现了。

预检（4 段 held-out 白天素材 / 1208 窗）看起来非常乐观：判错窗口的 `score`
中位 **0.048**，真人组 p10 **0.685** —— 窗口级**完全可分**，判错组里没有一个落在
真人区间内。

**② 解决思路**

先量化"信息是否存在"（预检通过），再做**受控消融**：两臂用**完全相同的数据集**，
只在一处不同 —— `train_v2.py --score-channel` 是否把这一路喂给模型。

实现上不新增输入维：`INPUT_DIM` 保持 192，复用两个恒定废维
（`51`=原 `cg_y`、`57`=原 `cg_y_norm`，归一化后恒 ≈ 0，全仓无人读取）。
PV 数据没有检测框，用掩码维显式标记"这条路没有信号"，以免 20% 的真人数据被推成非人。

**③ 怎么做的**

- 抽点缓存新增 `*_scores.npy`；特征构建支持 `score` / `has_score`；PV 传 `(0, 0)`
- `score` 在漏检帧上按 `confs` 同样插值（留 0 会造出"有人却突然掉到 0"的人造尖峰）
- 是否启用由**模型自己的 sidecar meta** 决定（`uses_score`），推理侧三分支分派，
  保证新旧两代权重用同一个 `realtime_detect.py` 都正确
- 2 臂 × 2 种子 = 4 轮训练；核心 KPI 用 `eval_nonperson_effect.py`
  （LOSO **看不见** NON_PERSON，它的 support 恒为 0）

**④ 结果如何**

| 指标 | 对照（无 score） | 处理（有 score） |
|---|---|---|
| 正常 Le2i 7 段 | 全 0 ✅ | 全 0 ✅ |
| 跌倒 5 段 首DANGER 均值 | 181.4 / 179.8 | 180.2 / 186.6 |
| 真实 6 段 首DANGER 均值 | 154.0 / 145.8 | **117.3 / 123.8** |
| **held-out 非人判定率** | **67.9% / 65.6%** | **60.2% / 58.7%** |

**❌ 不采纳。** 核心指标稳定劣化 **7.3 个点**，两臂无重叠（处理臂最大 60.2% <
对照臂最小 65.6%）。真实组的"改善"逐视频看不稳健（pd2、stair2 支持；stair1 明确反对；
pd4 两种子自相差 104 帧）。

**机制消融**：在 score 模型内部把该通道在标准化空间归零，判定率 60.2%→41.1%、
58.7%→47.4% —— 通道**确实被模型用了**（贡献 11–19 点），但启用它之后整体反而更差，
判 `SAFE` 的比例从 ~19% 升到 ~26–31%。这是典型的**捷径挤出其余通路**：多给一路强
信号，几何通路的判别力被摊薄。

**方法论教训（本轮最重要的一条）**

> **"信息可分" ≠ "信息是增量的"。**

预检证明了"判错窗口的 score 与真人完全可分"，据此判定"值得做"——但**判对组**
（832 窗，`NON_PERSON`）的 score 中位也只有 0.078。也就是说：**模型不靠 score
已经做到 68.9%**，score 提供的是"模型早就从几何量里学到的东西"，还顺带让它偷懒。
下次预检应当直接量"**现有模型在给定该特征条件下的条件误差**"，而不是"该特征本身
是否可分"。

**本轮另外三个实现陷阱**（详见 [tuning-log.md](tuning-log.md)）：

1. 消融把某一维置零后，它的 `norm` `std` 会塌到 `1e-8`，而推理侧算出来的是 ±5e-6
   的浮点噪声 → **z = ±274**，模型恒报 DANGER。**任何"置零"型消融都必须同时处理
   它在 `norm` 里的方差。**
2. `X[:, :, [51, 57]] = 0` 只清掉了 `pos` 段，`vel`/`acc` 里仍留着 score 的差分 →
   对照臂漏气。六维必须一起清。
3. 门控只加在了 `realtime_detect.py`，离线评估 harness 没加 → 又复现了一遍陷阱 1。

**顺带发现的一个更重要的既有问题**：`x_v2.npy` 构建于 **10-14 08:51**，而
`conf 0.05→0.02` 的提交在 **10-14 22:19**（晚 14 小时）。**当前生产模型是在
conf=0.05 抽的关键点上训练的，而推理一直用 conf=0.02。** 本轮重抽顺带修好了它，
但也暴露出：不带 score 时真实组首 DANGER 从 125.7 退化到 149.9 ——
"抽取配置对齐"本身可能带来真实段退化，需要单独复查。

## 3. 方法论：这 13 次优化教了我们什么

### 3.1 怎么"看"问题

**1. 先量化，再动手。**
10 次优化里没有一次是"感觉这样改改看"。每次都是先拿到数字
（特征差 10.12、222/990 帧零检出、47/51 帧被质量门滤掉、score 差 30 倍……），再决定改什么。

**2. 文档会撒谎，回数据核对。**
`nonperson_meta.json` 与 `README.md` 都声称 `NON_PERSON` 来自 `Home_02` 47/57（95 个窗口）。
回数组一数：class 3 = **0**；再一看，那两段视频**始终有人**。
→ **"记录存在"不等于"数据落地"。涉及数据来源的结论，一律回数组数。**

**3. 区分"模型不行"和"流水线把好东西滤掉了"。**
难例集里 51 个零检出帧，**47 帧裸 YOLO 其实给出了框**。
如果只看最终输出，会误判成"模型能力不足，需要更多训练数据"，方向就全错了。

**4. 直觉往往错，测了才知道。**
- 以为是"人动得快导致丢框" → 实测同一轨道帧间位移中位数只有 9.1px，**从未越过阈值**；
  越阈值的是"**框在变形**"。
- 以为是"关键点置信度高说明是人" → 实测**车的 0.718 比真人的 0.347 还高**。
- 以为是"缓冲区复用了上一帧特征导致历史框" → A/B 删掉那一行，历史框**一字不差**。

### 3.2 怎么改代码

**5. 训练与推理的预处理必须一模一样。**
优化 1 的根因：训练每帧取一人，推理把所有人写进同一个缓冲区 → 特征差放大 **11.8 倍** →
模型看到"剧烈失控的运动"就报跌倒。**这类不一致不会有任何报错，只会让效果莫名变差。**

**6. 分清各环节的职责，别让一个阈值干两件事。**
"门负责语义判别，`conf` 决定召回"；`conf=0.05` 把关系用反了 ——
它一边拦物品（拦不住），一边把夜间真人一起拦掉。

**7. 多处重复实现的逻辑，每条路径都要单独验证。**
`PersonTracker.update()` 有**两个分支**各自维护移除逻辑，只改主循环不生效，
僵尸轨道照样活 61 帧。用 20 行最小复现才暴露。

**8. 阈值要结合上下文，不能只看单一指标。**
两段式质量门的依据是**同一帧内的对比**：真人关键点低但**框置信度高**；家具/车罩两者都低。
单看"关键点低"就拒，必然误伤夜间真人。

**9. 改动前先定死通过门槛**，避免事后找理由。
例：车类交叉验证预先定"真人误杀必须为 0"，结果实测 9/105 → 直接判不通过、不接入。

### 3.3 怎么训练、怎么对待模型

**10. 定义了类别 ≠ 具备该能力。**
`RiskClassifierV2` 输出 4 类，但 class 3 样本数 **0** ⇒ 那条 `NON_PERSON → 风险强制 0`
是**死代码**。**每次训练前先看 label 分布**，别信代码里定义了就叫有。

**11. 特征决定上限 —— "学不会"先查"输入里有没有"，而不是先换更复杂的模型。**
> 这一条在优化 11 与优化 12 各拿到一次实测：换成同量级的 TCN（编码器）、换四种池化，离线指标都基本不动、端到端也没有改善（部分还更差）。而 9 条已知缺陷里没有一条是"时序函数不够强"导致的。**连续两次架构侧消融为负，是"瓶颈在信息与数据"最直接的证据。**

这辆车的 `score` 与真人差 **30 倍**，但它不在 192 维特征里。
于是模型只能在几何上硬凑，而几何上它确实像人。
→ **遇到"模型学不会"，第一件事不是加数据，而是问：这个判别信息在输入里吗？**

**12. 模型会学捷径，而且捷径比"学不会"更难发现。**
- 负样本全场抖动 → 学到"**抖 ⇒ 非人**"，于是静止的停放车辆反而漏掉（优化 10）
- 负样本是手持素材 → 学到"**镜头动 ⇒ 非人**"（采集规范早已警告，这次真实发生）
→ **每给一批负样本，都要问：它们是否共享了某个与目标无关的属性？**

**13. "窗口数"不是样本量。**
2174 个窗口 → 互不重叠只有 **223 个**（滑窗重叠 27/30 帧，天然夸大 ~10 倍），
且全部来自 **1 个场景**。
→ **评估数据量一律用「互不重叠窗口数 × 场景数」。**

**14. 重训类对比必须固定随机种子。**
否则 baseline 自身 12pp 的波动会被当成 16pp 的"退化"写进结论。

### 3.4 怎么验证

**15. 端到端回归是唯一裁判，离线分析只能指方向。**
同一个坑出现两次：
- 优化 5：难例集显示"完全干净"，Le2i 回归里沙发让空镜头报警提前 62 帧
- 优化 8：离线说"0 误杀"，端到端实测误杀 9/105

**16. 评测口径决定了你能看见什么。**
- 难例集只能表达"帧内**有无**检出"，看不见"检出数**多于**实际人数"（沙发躲过）
- `hard_cases` 是**帧级检出**评测，看不见"**类别判错**"（优化 10 那辆车检出是对的）
→ **每次遇到"评测没报错但实际有问题"，就该扩口径。**

**17. 一次改动要同时报"目标指标"和"回归指标"。**
每次验收都同时看：目标指标（难例集召回 / 非人判定率）+
回归指标（Le2i 正常 7 段是否仍 0 报警 + 跌倒首 DANGER 是否推迟）。

**18. 先写工具，再改东西。**
优化 4 之前只能凭感觉；建了难例集与双口径评测之后，后面每一步都有数字可依。
**基础设施的价值在第四次、第五次优化时才显现。**

**19. 「信息可分」≠「信息是增量的」。（优化 13 的教训）**
预检显示"判错窗口的 `score` 与真人完全可分"（0.048 vs 0.685，零重叠），据此判定
"值得做"。但**判对组自己不靠 `score` 已经做到 68.9%**，这一路提供的是模型早从几何量
里学到的东西，还顺带让它偷懒（判 `SAFE` 的比例从 19% 升到 31%）。
→ 预检应当直接量「**现有模型在给定该特征条件下的条件误差**」，
而不是「该特征本身是否可分」。可分的特征多得很，能减少现有模型误差的才值得加。

**20. 「把某一维置零」的消融必须同时处理它在 `norm` 里的方差。**
置零后那一维的 `std` 会塌到 `1e-8`，而推理侧算出来的是 ±5e-6 的浮点噪声
→ z = ±274 → 模型恒报 DANGER，且**不报任何错**。同理，门控要落在
**所有**喂模型的入口（`realtime_detect.py` **与**离线评估 harness），
不能只加一处。这两个坑本轮各踩了一次。

## 5. 术语小抄

| 术语 | 含义 |
|---|---|
| **关键点 / keypoint** | 人体上的 17 个坐标点（鼻、眼、耳、肩、肘、腕、髋、膝、踝，COCO 定义） |
| **关键点置信度 / `kptconf`** | 每个关键点各自的可靠程度（0–1）。**不能用来判断"这是不是人"** —— 车的比真人还高 |
| **bbox score** | 模型对"这个框里是个人"的整体置信度。判别力最强的一个量；**2026-10-16 已实测把它接入特征，结论是整体反而更差（优化 13）** |
| **质量门** | `PoseExtractor._is_valid_person`，决定哪些候选"像是人"喂给下游。是**置信度**过滤器，不是语义过滤器 |
| **滑窗 / `WINDOW_SIZE` / `stride`** | 把时间序列切成 30 帧一段。`stride` 是滑动步长，窗口会重叠 → **窗口数 ≫ 独立样本数** |
| **192 维特征** | 每 30 帧窗口的输入：每帧 64 维（51 关键点 + 13 几何）→ 再拼 pos / vel / acc 各 64 |
| **vel / acc** | 相邻帧之差（速度）、再差一次（加速度）。192 维里 2/3 是它们，所以**抖动的权重很大** |
| **LOSO** | Leave-One-Scene-Out：按**场景**划分训练/测试，而不是按时间。防止同一场景的相似帧同时出现在两边 |
| **类别权重** | 样本少的类给更大权重，免得模型只顾多数类。本次 `NON_PERSON` 权重 3.045 vs `SAFE` 0.342 |
| **Focal Loss** | 让模型更关注"难分"样本的损失函数（本次 `gamma=2.0`） |
| **温度缩放 / temperature** | 训练后校准，让输出的概率值更可靠（本次 T≈2.14） |
| **EMA 平滑** | 指数滑动平均，让风险分数不会因单帧抖动突变（`smooth = α·新值 + (1−α)·旧值`） |
| **held-out** | 完全没参与训练的素材/场景，用来验证"是不是真学会了"而不是"背下来了" |
| **端到端回归** | 让**真实的完整流程**跑一遍固定视频集，比较报警帧。区别于只测某一环的离线分析 |
| **难例集** | 人工标注的一小批困难帧（本次 114 帧），用来量化召回/误报 |
| **捷径 / shortcut** | 模型学到了某个与目标无关但恰好相关的属性（如"画面在动 ⇒ 非人"）。**很难发现，且会静默失效** |
